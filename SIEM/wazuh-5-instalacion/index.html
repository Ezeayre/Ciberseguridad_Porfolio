Instalé Wazuh 5.0 paso a paso, con mis propios certificados, y enrolé un agente Linux

🖥️ Dashboard
⇄

(HTTPS)
VM 2 · wazuh-agent (Ubuntu Server 24.04)
🛰️ Agente Wazuh

Dos VMs en VMware Workstation Player, en la misma red virtual, administradas por SSH. El servidor tiene 2 vCPU, 4 GB de RAM y swap; el agente, 2 vCPU y 4 GB.

📋 ¿De qué trata este proyecto?

Es el laboratorio base que uso para mis proyectos con Wazuh 5.0. Instalé los tres componentes centrales (indexer, manager y dashboard) uno por uno, sin instalador asistido, para entender qué hace cada uno y cómo se conectan. Después enrolé un agente Linux con un token, que es el método nuevo de 5.0.

Lo más importante que aprendí: todo en Wazuh se comunica con TLS, y casi todos los problemas que tuve fueron de certificados.

🔐 Certificados y CA: por qué son lo primero

Una CA (autoridad certificante) es un certificado raíz que firma los certificados de cada componente. Cuando el manager se conecta al indexer, o el agente al manager, cada uno verifica que el certificado del otro esté firmado por la misma CA. Si no coincide, la conexión se rechaza.

Por eso lo primero es generar una sola CA (root-ca.pem) y, con ella, un certificado para cada componente.

💡 Si dos componentes usan certificados de CAs distintas, no confían entre sí. Ese fue el origen de casi todos mis errores.

🧪 Instalación paso a paso

El orden importa: primero los certificados, después indexer → manager → dashboard, y al final el agente.

1
Generar los certificados y la CA
▼

Usé la herramienta de certificados de Wazuh (wazuh-certs-tool). Primero edité su config.yml, que venía con IPs de ejemplo, y cargué la IP de mi servidor para los tres componentes.

Con eso generé la CA y los certificados de cada componente, y los empaqueté para copiarlos a cada uno:

bash ~/wazuh-certs-tool-5.0.0-beta2.sh -A
tar -cvf ~/wazuh-certificates.tar -C ~/wazuh-certificates/ .
2
Indexer
▼

El indexer guarda los eventos y, en 5.0, también corre el motor de detección. Lo instalé, le copié solo sus certificados con dueño y permisos restringidos, y lo levanté:

sudo apt-get install wazuh-indexer
sudo mkdir -p /etc/wazuh-indexer/certs
sudo tar -xf ~/wazuh-certificates.tar -C /etc/wazuh-indexer/certs/ ./indexer.pem ./indexer-key.pem ./root-ca.pem
sudo chown -R wazuh-indexer:wazuh-indexer /etc/wazuh-indexer/certs/
sudo chmod 500 /etc/wazuh-indexer/certs
sudo chmod 400 /etc/wazuh-indexer/certs/indexer-key.pem
sudo systemctl enable --now wazuh-indexer

Un detalle nuevo de 5.0: dentro del servicio del indexer aparece wazuh-engine, el motor que aplica decoders y reglas.

Después cargué la configuración de seguridad (usuarios, roles y permisos):

sudo /usr/share/wazuh-indexer/bin/indexer-security-init.sh
3
Manager
▼

El manager recibe los eventos de los agentes y los manda al indexer. Lo instalé, lo apunté al indexer con su certificado de cliente y la CA, y lo levanté:

sudo apt-get install wazuh-manager
sudo systemctl enable --now wazuh-manager

La conexión al indexer usa la misma CA (root-ca.pem). En el log se ve Event processing is now active: el manager ya procesa eventos.

4
Dashboard
▼

El dashboard es la interfaz web. Lo instalé y cargué sus credenciales en el keystore con resolve-credentials, que las toma de /etc/wazuh/credentials.env (archivo legible solo por root):

sudo apt-get install wazuh-dashboard
sudo /usr/share/wazuh-dashboard/bin/resolve-credentials --prestart
sudo systemctl restart wazuh-dashboard
5
Enrolamiento del agente con token
▼

En 5.0 el agente se enrola con un token de un solo uso que genera el manager. El token incluye la CA del manager, así el agente puede verificar que se conecta al servidor correcto.

En el manager se ve el token: endpoint, vencimiento y usado 1/1.

En el agente lo usé para enrolarlo. La respuesta confirma el ID, el puerto 1517 y que instaló la CA (trust anchor):

sudo /var/ossec/bin/wazuh-agent-auth --token-file /root/wazuh-enrollment/token
sudo systemctl enable --now wazuh-agent

Resultado: el agente 001 aparece activo en el dashboard.

⚠️ El agente guarda su clave en /var/ossec/etc/client.keys, con permisos 640. No muestro su contenido porque es la credencial del agente.

🔧 Problemas que tuve y cómo los resolví

ProblemaSolución
El config.yml de certificados venía con IPs de ejemploLo edité con la IP real del servidor antes de generar nada
El certificado de remoted no encadenaba con la CA, y el agente no podía confiar en el managerAlineé los certificados para que salieran todos de la misma CA
El dashboard daba ConnectionError ... certificate al conectar con el indexerRevisé qué CA usaba cada componente y las hice coincidir
El indexer llenó el disco del servidorAmplié el disco virtual de 40 a 60 GB y extendí la partición, el volumen LVM y el filesystem
Los servicios fallaban al arrancar por timeout en una VM con poca RAMLos levanté a mano en orden (indexer → manager → dashboard)

💡 Lo que me llevo

✅ SIEMPRE HACER:
  • Generar una sola CA y todos los certificados desde ella
  • Respetar el orden: indexer → manager → dashboard
  • Darle a cada componente solo sus certificados, con permisos restringidos
  • Revisar el log de cada servicio cuando algo no conecta
❌ NUNCA HACER:
  • Mezclar certificados de distintas CAs
  • Mostrar contraseñas, tokens válidos o el contenido de client.keys
  • Darle al servidor un disco justo: el indexer crece rápido
